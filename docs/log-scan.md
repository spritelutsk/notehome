# Ежедневный разбор журналов и вкладка «Логи»

`server/log-scan.js`, ручки `/api/admin/logs*` в `server/routes/admin.js`, вкладка `#view-logs`
в интерфейсе.

Журналы писались и раньше ([docs/web-access-log.md](web-access-log.md)), но читал их человек:
чтобы заметить скан или ошибку приложения, надо было зайти по ssh и вспомнить нужный `grep`.
Ровно этим занята сессия за 18 августа — и результат её пропадает, пока кто-нибудь не повторит
проверку руками. Здесь то же самое делается само, каждое утро.

Разбор только смотрит и считает. Ничего не блокируется и не удаляется: при CGNAT снаружи
стучаться некому, а внутри сети банить самих себя незачем — та же причина, по которой
в журналах нет fail2ban.

## Когда и за какой срок

Каждый день в 8:00 за прошедшие сутки. То есть отчёт, готовый к утру, покрывает ровно
предыдущее утро и до сих пор.

Расписание держит `setTimeout`, который каждый раз планирует следующий заход заново, — приём
взят из `server/link-check.js`: `setInterval` на сутки уползает от восьми утра и сдвигается
навсегда при переходе на зимнее время.

**При старте разбор не запускается.** Перезапуск сервиса — не повод перечитывать журналы,
а при частых рестартах история засорилась бы отчётами за одни и те же сутки. Обратная
сторона: если приложение перезапускают каждый день после восьми, автоматический разбор
не пройдёт никогда — в этом случае жать «Проверить сейчас».

## Что читается

Источник|Что оттуда берётся
`journalctl -u spritenote`|ошибки приложения, перезапуски сервиса, открытия веб-терминала
`web-access.log`|все запросы: сканеры, неудачные входы, 4xx/5xx, обращения по голому IP
`web-unknown.log`|обращения по чужому имени сайта
`web-external.log`|гости из-за пределов домашней сети и тайлнета
`web-error.log`|обрывы TLS и прочие ошибки nginx
`nftables-web.log`|TCP-подключения и «странные» пакеты (ACK-скан, FIN, NULL, Xmas)

Каждый файл читается вместе со вчерашней ротацией (`.1` и `.1.gz`): сутки почти всегда
пересекают полночь, когда logrotate уводит текущий файл, и без этого половина окна пропала бы.

С конца файла берётся не больше 8 МБ, первая строка после обрезки отбрасывается как заведомо
обрубленная. Это про SD-карту: под заливкой скана суточный журнал бывает в сотни мегабайт.

Пути к файлам прибиты гвоздями — их задаёт не приложение, а конфигурация nginx и rsyslog
из `scripts/`. Переменные `LOG_SCAN_UNIT`, `LOG_SCAN_NGINX_DIR` и `LOG_SCAN_NFT_FILE` есть
только ради проверки на подставных файлах; в бою они не задаются.

### Права на чтение

Журналы принадлежат группе `adm` с правами `640`, поэтому **пользователь, под которым запущено
приложение, обязан состоять в `adm`** — иначе читать будет нечего. То же и с `journalctl`.
Проверка:

```bash
id -nG "$(systemctl show -p User --value spritenote)" | tr ' ' '\n' | grep -x adm
```

Выпадение из группы не проходит молча: недоступный источник попадает в раздел «Недоступные
журналы» и поднимает уровень всего отчёта до жёлтого. Это сделано намеренно — пустой отчёт при
нечитаемом журнале означает «не смотрели», а не «чисто», и молча выдавать «тревог нет» здесь
было бы враньём.

## Как устроен отчёт

Отчёт — объект, который целиком уходит на клиент и целиком же лежит в базе полем `report`
таблицы `log_reports` (JSON, а не колонки: разделы меняются вместе с кодом разбора, и
раскладка по колонкам означала бы миграцию при каждой правке). История подрезается до
90 последних записей.

```
generatedAt, windowFrom, windowTo, windowHours, scanHour
level      — худший уровень среди разделов: ok | warn | alert
alerts, warnings — сколько разделов на каком уровне
sources[]  — { id, label, error }, error = null, если файл прочитан
sections[] — { id, level, count, stats: [{label, value}], samples: [строки] }
```

**Разделы приходят кодами, а не готовым текстом** — как и ошибки во всём остальном проекте.
Русский и украинский текст лежит в `TRANSLATIONS` в `public/js/app.js` под ключами `log_<id>`
и `log_<id>_desc`. Новый раздел в разборе без пары ключей в словаре покажется на экране своим
кодом. Проверить, что все на месте:

```bash
node -e "
const fs=require('fs');
const app=fs.readFileSync('public/js/app.js','utf8');
const s=app.indexOf('const TRANSLATIONS = {'), e=app.indexOf('\n  };', s);
const T=eval('('+app.slice(s+'const TRANSLATIONS = '.length, e+4)+')');
const ids=[...fs.readFileSync('server/log-scan.js','utf8').matchAll(/section\('([a-z_]+)'/g)].map(m=>m[1]);
const miss=[...new Set(ids)].flatMap(i=>['log_'+i,'log_'+i+'_desc']).filter(k=>!T[k]);
console.log(miss.length ? miss : 'все разделы переведены');
"
```

### Уровни

`ok` — ничего; `warn` — есть на что посмотреть; `alert` — требует внимания. Пороги стоят
в самом разделе (`levelFor(count, warnAt, alertAt)`) и подобраны под домашний сервер: то, что
для публичного сайта фоновый шум, здесь означает, что кто-то приходил специально. Один запрос
на `/wp-login.php` — уже жёлтый, два десятка — красный.

Уровень всего отчёта — худший из разделов. Разделы, где ноль и спокойно, на экране
не разворачиваются: их полтора десятка, и экран из одних нулей прятал бы то немногое, ради
чего сюда заходят. Они уходят одной строкой «Без событий: …».

### Что считается запросом сканера

Список шаблонов — `PROBE_PATTERNS` в `server/log-scan.js`: `wp-login.php`, `.env`, `.git`,
phpMyAdmin, `cgi-bin`, `manager/html` и вообще любой `.php` (приложение на Node, своего `.php`
у него нет и быть не может).

Свои адреса под шаблоны не попадают намеренно, и это легко сломать: админка живёт на
`/api/admin`, а не на `/admin`, поэтому шаблон `^/admin` безопасен; `xterm.js` отдаётся
из `/vendor/xterm/`, поэтому вместо `/vendor/` стоит точный `/vendor/phpunit/`. Добавляя
шаблон, проверьте, что под него не попадает собственный адрес приложения, — иначе отчёт
станет ежедневно тревожить сам себя, и его перестанут читать.

## Ручки

Обе внутри роутера `/api/admin`, то есть за `requireAuth, requireAdmin`, и на публичном
адресе недоступны вместе со всем префиксом.

Ручка|Что делает
`GET /api/admin/logs`|последний отчёт (или `?id=N` — конкретный), список истории, час разбора
`POST /api/admin/logs/scan`|разбирает журналы прямо сейчас, сохраняет и возвращает тем же видом

Одновременных разборов не бывает: `runScan()` держит текущий промис и отдаёт его же второму
вызывающему. Иначе ночной таймер и кнопка «Проверить сейчас», совпав по минуте, читали бы
мегабайты с карты памяти в два потока.

`report: null` в ответе означает «разбор ещё ни разу не проходил» — обычное состояние в первые
сутки после обновления, клиент показывает это отдельным текстом.

## Вкладка

Видна там же и на тех же условиях, что «Панель управления», «Блокнот» и «Терминал»:
администратор **и** адрес, с которого доступен `/api/admin` (см.
[docs/admin-and-terminal.md](admin-and-terminal.md)).

Кнопки: «Обновить» перечитывает последний отчёт, «Проверить сейчас» запускает разбор,
выпадающий список справа открывает отчёты за прошлые дни (появляется со второго отчёта).

**Про безопасность отрисовки.** В строках отчёта лежит то, что прислал чужой клиент: путь
запроса, User-Agent, заголовок `Host`. Это ровно тот текст, который сканер может подобрать
так, чтобы он стал разметкой на странице администратора. Всё, что уходит в `innerHTML`
в разделе «Логи сервера» в `app.js`, обязано пройти через `escapeHtml()`.
