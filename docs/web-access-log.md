# Журнал обращений на 80 и 443

Кто стучался в веб-порты, с каким именем, чем закончилось. Два слоя: nginx пишет запросы,
nftables — сами TCP-подключения. Второй нужен потому, что сканер, отправивший SYN и ушедший,
до HTTP не доходит и в `access.log` не появляется вообще.

## Что до этих портов доходит на самом деле

Важно понимать до чтения журналов, иначе выводы будут неверные.

**На 443 извне не приходит ничего.** Провайдер держит абонента за CGNAT, проброс портов
на роутере невозможен, сертификат выпущен через DNS-01 и входящих соединений не требует.
Всё, что попадает в журнал 443, — домашняя сеть и localhost.

**Внешний трафик приходит на 80.** Наружу приложение смотрит через Tailscale Funnel: TLS
снимает сам `tailscaled` и проксирует соединение на `127.0.0.1:80`. Поэтому у внешнего клиента
`$remote_addr` всегда локальный, а настоящий адрес лежит в `X-Forwarded-For` — он пишется
в каждую строку полем `xff=`. Ищете реальных гостей снаружи — смотрите это поле, а не первую
колонку.

## Слой 1: nginx

Настройка одна на все vhost — [`scripts/nginx-access-logging.conf`](../scripts/nginx-access-logging.conf)
лежит в `/etc/nginx/conf.d/`, то есть в контексте `http`, и наследуется и 443-м, и обоими
80-ми блоками. Новый сайт получит журнал автоматически.

Штатный `/var/log/nginx/access.log` остался нетронутым: несколько директив `access_log`
на одном уровне разрешены, старый файл пишется в прежнем формате.

Файл|Что внутри
`web-access.log`|все запросы на 80 и 443
`web-unknown.log`|Host не из списка известных имён
`web-external.log`|источник вне домашней сети и тайлнета
`web-error.log`|оборванные рукопожатия TLS и прочее, до чего запрос не дожил

Строка выглядит так:

```
2026-08-11T11:14:19+03:00 192.168.1.104:35542 -> :443 xff=- host="192.168.1.104" sni="-"
"GET /api/health HTTP/2.0" 200 11b rt=0.005 tls=TLSv1.3/TLS_AES_256_GCM_SHA384 ua="curl/8.14.1"
```

`sni` стоит рядом с `host` не для симметрии. SNI клиент называет в открытом виде ещё
до шифрования, а `Host` пишет уже внутри канала, и подделать его ничего не стоит. Пустой
`sni` при заполненном `host` означает, что клиент пришёл по голому IP и имени не спрашивал, —
обычный браузер так не делает.

### Что считается «своим»

Карта `$log_unknown_host` перечисляет известные имена машины: домен DuckDNS, имя узла
в тайлнете, адрес в LAN, адрес в тайлнете, hostname, `localhost`. Остальное попадает
в `web-unknown.log`.

Список привязан к конкретной машине. **Сменился адрес в LAN или имя узла — правьте карту**,
иначе собственный трафик начнёт падать в журнал подозрительного и обесценит его.

### Как считается «внешний»

Проверять один `$remote_addr` бесполезно: у трафика через Funnel он всегда `127.0.0.1`,
и настоящий гость снаружи выглядел бы как локальный. Поэтому адрес берётся из двух
источников — `$remote_addr` и первый элемент `X-Forwarded-For`, — и запрос считается
внешним, если наружу смотрит хотя бы один.

Из `X-Forwarded-For` берётся самый левый адрес: заголовок бывает списком
`клиент, прокси1, прокси2`, где всё правее клиента дописано по дороге.

Поведение при чужом Host не меняется: запрос обслуживается как раньше, строка просто
дополнительно пишется в срез. Закрывать такие обращения через `return 444` осознанно
не стали — это сломало бы HTTPS по голому IP, а сейчас важнее наблюдать, а не блокировать.

### Уровень error_log

`web-error.log` пишется на уровне `info` — заметно подробнее стандартного. Здесь оседает то,
чего в `access.log` не будет никогда: неудачные рукопожатия TLS, открытый HTTP в 443-й порт,
клиенты, закрывшие соединение до ответа.

В конфиге две директивы `error_log` подряд, и первая обязательна. `error_log` не складывается
между уровнями: без строки, повторяющей штатный путь, вся диагностика http ушла бы из
`/var/log/nginx/error.log`. Файл растёт быстрее ожидаемого — меняйте `info` на `notice`.

## Слой 2: nftables

[`scripts/nftables-log-web.nft`](../scripts/nftables-log-web.nft) заводит таблицу `inet log_web`
с `policy accept` и единственным действием `log`. Она ничего не фильтрует — это журнал,
а не файрвол.

Таблица отдельная намеренно. Цепочками в `table ip filter` управляет сам `tailscaled` через
`iptables-nft`, трогать их нельзя; два независимых семейства не конфликтуют. Приоритет
`filter - 10` ставит журнал раньше цепочек Tailscale, иначе отброшенное ими в записи не попало бы.

Пишутся два вида событий:

- `WEB-CONN` — начало соединения (`ct state new`). Без фильтра по состоянию в журнал шла бы
  каждая пачка пакетов открытой сессии;
- `WEB-ODD` — пакет не на установленное соединение и не начало нового: ACK-скан, FIN/NULL/Xmas.

Оба правила ограничены по частоте. Это защита SD-карты: под заливкой скана журнал забил бы
раздел за минуты. Записи сверх лимита теряются, но соединения не блокируются — `policy accept`
действует независимо от того, попала строка в файл или нет.

Загружает таблицу юнит `spritenote-log-web.service`, до `nginx.service`. Файл начинается
с `destroy table`, поэтому `restart` и `reload` не плодят дублей правил.

Записи ядра уводит в свой файл правило `/etc/rsyslog.d/30-log-web.conf` с `& stop` — иначе
они дублировались бы в `/var/log/syslog` и `/var/log/kern.log` и под сканом сделали бы общий
журнал нечитаемым.

## Как смотреть

Каждое утро в 8:00 эти же файлы разбирает само приложение и складывает итог во вкладку «Логи»
в админке — см. [docs/log-scan.md](log-scan.md). Ручной разбор ниже никуда не делся: отчёт
показывает срез за сутки, а «что было на той неделе» по-прежнему смотрят руками.

```bash
# кто приходил снаружи домашней сети
sudo cat /var/log/nginx/web-external.log

# обращения по чужому Host — за сегодня
sudo grep "$(date +%F)" /var/log/nginx/web-unknown.log

# топ источников за всё время
sudo cat /var/log/nginx/web-access.log | awk '{print $2}' | cut -d: -f1 | sort | uniq -c | sort -rn

# запросы без SNI на 443: пришли по голому IP
sudo awk '/-> :443/ && /sni="-"/' /var/log/nginx/web-access.log

# подключения на уровне пакетов, только адрес и порт назначения
sudo grep -oE 'SRC=[0-9.]+ .*DPT=[0-9]+' /var/log/nftables-web.log | tail -20

# неудачные рукопожатия TLS
sudo grep -i 'SSL\|handshake\|plain HTTP' /var/log/nginx/web-error.log
```

## Ротация

Логи nginx накрыты штатным `/etc/logrotate.d/nginx` по маске `/var/log/nginx/*.log` — новые
файлы туда попали сами, отдельного правила не нужно. Для `nftables-web.log` заведён
[`scripts/logrotate-spritenote-log-web`](../scripts/logrotate-spritenote-log-web) с той же
глубиной: ежедневно, 14 копий, со сжатием. Глубина совпадает намеренно, чтобы «за прошлую
неделю» означало одно и то же в обоих местах.

## Установка на чистой машине

```bash
sudo cp scripts/nginx-access-logging.conf /etc/nginx/conf.d/access-logging.conf
# в карте $log_unknown_host и geo подставить адреса и имена своей машины
sudo nginx -t && sudo systemctl reload nginx

sudo mkdir -p /etc/nftables.d
sudo cp scripts/nftables-log-web.nft /etc/nftables.d/log-web.nft
sudo cp scripts/rsyslog-log-web.conf /etc/rsyslog.d/30-log-web.conf
sudo cp scripts/logrotate-spritenote-log-web /etc/logrotate.d/spritenote-log-web
sudo cp scripts/spritenote-log-web.service /etc/systemd/system/
sudo systemctl restart rsyslog
sudo systemctl daemon-reload
sudo systemctl enable --now spritenote-log-web
```

Проверка: `sudo nft list table inet log_web` показывает два правила `log prefix`,
а обращение к приложению добавляет строки в `web-access.log` и `nftables-web.log`.

## Чего здесь нет

Журнал только записывает. Автоматической блокировки по числу попыток (fail2ban или
`nft set` с таймаутом) нет — при CGNAT снаружи стучаться некому, а внутри сети банить
самих себя незачем. Появится прямой внешний адрес — вот тогда это и понадобится.
