# Модель данных

Схема для свежей установки — `scripts/init-db.sql`. Колонки, добавленные после первого релиза,
дублируются в `server/schema.js` и доезжают на уже развёрнутую БД при старте приложения.
**Добавляя колонку, правьте оба файла.**

## `users`

| Колонка | Тип | Заметки |
|---|---|---|
| `id` | INT PK | |
| `email` | VARCHAR(255) UNIQUE | всегда нормализован: `trim().toLowerCase()` |
| `password_hash` | VARCHAR(255) | bcrypt, 10 раундов |
| `is_admin` | TINYINT(1) | первый зарегистрировавшийся получает 1 |
| `settings` | TEXT NULL | JSON пользовательских настроек, `NULL` = всё по умолчанию |
| `created_at` | DATETIME | |

### `settings` — настройки пользователя

Живут на аккаунте, а не в `localStorage`. Причина: две учётки на одном компьютере не должны
делить настройки, а одна учётка на телефоне и на ноутбуке — должна.

Единственный источник правды — `SETTINGS_SPEC` в `server/user-settings.js`:

```js
const SETTINGS_SPEC = {
  contentViewMode: { default: 'grid', values: ['grid', 'list'] },
};
```

Добавить настройку = добавить туда запись. Из спецификации автоматически следуют значения по
умолчанию, валидация и то, что запишется в БД. На клиенте есть зеркало — `DEFAULT_SETTINGS`
в `public/js/app.js`; его надо держать в синхроне вручную.

Правила разбора (`parseSettings`) намеренно снисходительны: битый JSON, неизвестный ключ или
значение вне списка молча заменяются на дефолт. Кривая строка в колонке не должна ломать вход
в систему. Запись (`sanitizePatch`), наоборот, строгая: неизвестные ключи отбрасываются, и если
после фильтрации не осталось ничего — ручка отвечает `400 invalid_request`. Поэтому попытка
записать в настройки, например, `{"isAdmin": true}` ничего не даст.

API:

- `GET /api/auth/me` → `{ user: { id, email, isAdmin, settings } }`
- `PUT /api/auth/settings` — частичный патч, отвечает полным объектом настроек

`requireAuth` кладёт уже разобранные настройки в `req.user.settings`, так что серверному коду
парсить их повторно не нужно.

## `sessions`

| Колонка | Тип | Заметки |
|---|---|---|
| `token` | CHAR(64) PK | 32 случайных байта в hex |
| `user_id` | INT FK → users | `ON DELETE CASCADE` |
| `expires_at` | DATETIME | по умолчанию +30 дней (`SESSION_TTL_DAYS`) |

Токен лежит в httpOnly-куке `spritenote_session` (`SameSite=Lax`, `secure` — когда запрос пришёл
по HTTPS). Протухшие сессии удаляются лениво, при обращении. Смена пароля удаляет все сессии
пользователя, **кроме** текущей.

## `nodes` — дерево

Одна таблица на всё: и папки, и содержимое. Иерархия — через `parent_id` (adjacency list),
`parent_id IS NULL` = корень.

| Колонка | Тип | Заметки |
|---|---|---|
| `id` | INT PK | |
| `user_id` | INT FK → users | `ON DELETE CASCADE` |
| `parent_id` | INT FK → nodes NULL | `ON DELETE CASCADE` — срабатывает только при удалении навсегда |
| `type` | ENUM | `folder` / `link` / `text` / `doc` |
| `name` | TEXT | |
| `description` | TEXT NULL | |
| `url` | VARCHAR(2048) NULL | только для `link` |
| `content` | MEDIUMTEXT NULL | только для `text` |
| `file_path`, `file_size`, `file_original_name` | | только для `doc` |
| `deleted_at` | DATETIME NULL | корзина: `NULL` — узел живой, дата — когда его удалили |
| `is_favorite` | TINYINT(1) | избранное, отдельная секция сверху боковой панели |
| `link_status` | VARCHAR(40) NULL | живость ссылки: `NULL` — не проверяли, `ok`, иначе код причины |
| `link_checked_at` | DATETIME NULL | когда последний раз ходили по адресу |

Индекс `idx_user_parent (user_id, parent_id)` — под основной запрос «дети такой-то папки».

### `deleted_at` — корзина

Удаление мягкое: `DELETE /api/nodes/:id` не стирает строки, а проставляет `deleted_at = NOW()`
узлу и всему его поддереву. Отдельной таблицы нет, перестройки модели тоже — но платой за это
служит правило, которое легко нарушить:

> **`AND deleted_at IS NULL` обязателен в каждом запросе, который считает дерево живым.**

Сейчас таких мест пять: список (`GET /api/nodes`), экспорт, поиск существующих узлов при
импорте, `getOwnNode()` и проверка потомков при перемещении. Забыть фильтр — значит показать
содержимое корзины как обычные элементы дерева.

Что показывать в корзине, определяется без второй колонки: удалённый узел попадает в список
«Недавно удалённое», только если его родитель жив или его нет вовсе. Удалили папку — в списке
одна строка на неё, а не на каждый элемент внутри.

Пачку одного удаления связывает сама метка: один `UPDATE` проставляет всему поддереву
одинаковый `deleted_at` с точностью до секунды, и восстановление снимает метку ровно у тех
узлов, у которых она совпадает с корневой. Поэтому потомок, удалённый раньше и отдельно, при
восстановлении родителя останется в корзине — со своим сроком и своей строкой. `UPDATE`
в обе стороны пишет `updated_at = updated_at`: удаление не правка содержимого, и дата изменения
после возврата из корзины обязана остаться прежней.

Строки исчезают по-настоящему в трёх случаях: «Удалить навсегда», «Очистить корзину» и
автоочистка в `server/trash.js` (`TRASH_TTL_DAYS = 30`, проход при старте и раз в шесть часов).
Каскад по `parent_id` уносит поддерево из БД, но **файлы `doc` каскад не удаляет** — их пути
собираются до `DELETE` и стираются с диска явно. Пока узел лежит в корзине, его файл остаётся
на месте и занимает диск: подсчёт «Данные» в панели управления это учитывает и не фильтрует
удалённое намеренно.

Особенности, о которых стоит знать:

- **Дерево целиком уезжает на клиент одним плоским списком** (`GET /api/nodes`), и вся навигация,
  хлебные крошки и поиск считаются в браузере. Для личной базы в сотни узлов это проще и быстрее,
  чем рекурсивные запросы. Если база вырастет до десятков тысяч узлов — вот это место и надо будет
  переделывать первым.
- **Родителем может быть только `folder`** — проверяет `assertValidParent()`.
- **Перемещение проверяет циклы**: нельзя перенести папку в саму себя или в свою же подпапку.
- **Файлы `doc` лежат вне БД**, в `data/uploads/<user_id>/<случайное_имя><ext>`. Оригинальное имя
  хранится отдельно, в `file_original_name` — на диск оно не попадает, поэтому подсунуть путь
  через имя файла нельзя. Каскад БД файлы не удаляет: при удалении аккаунта каталог сносится
  явно, в `routes/auth.js`, а при чистке корзины — в `routes/nodes.js` и `trash.js`.

## Живость ссылок

`link_status` заполняет `server/link-check.js`: обход идёт **раз в сутки, в 3:00**, и за один
раз проверяет все ссылки, которым пора (заходами по 20, по одной с паузой в 1,5 с, не больше
500 за ночь). При старте приложения обход не запускается — перезапуск сервиса не повод идти
в интернет. Следующий запуск планируется заново после каждого, а не через `setInterval`:
так время не уползает от 3:00 и перевод часов не сдвигает обход навсегда. Своего похода по адресу
там нет — `safeFetch` берётся из `server/link-summary.js` целиком, вместе с проверкой IP,
пиннингом соединения и ручным разбором редиректов. **Второй реализации похода по
пользовательскому URL в проекте быть не должно.**

Наружу уходит код, а не текст: `ok`, `http_404`, `http_403`, `http_401`, `http_429`,
`http_5xx`, `http_error`, `unreachable`, `dns_failed`, `network_unreachable`,
`url_not_allowed`, `invalid_url`, `too_many_redirects`. Русский и украинский текст к ним —
ключи `link_status_*` в `app.js`.

**Не всякий не-`ok` означает «ссылка умерла».** Коды `http_401`, `http_403`, `http_429`
и `network_unreachable` — это «сервер отказался с нами разговаривать»: за ними обычно стоит
защита от ботов, и сайт прекрасно открывается в браузере. Такие ссылки помечаются серым
знаком вопроса, в «Битые ссылки» не попадают и в счётчик не идут. Список лежит в константе
`UNVERIFIABLE` в `server/link-check.js`, и у него есть **ручное зеркало в `app.js`** — при
изменении правьте оба.

Сетевые отказы (`unreachable`, `http_5xx`) проверяются дважды с паузой: чужой сервер может
моргнуть, и одного неудачного захода мало, чтобы объявить ссылку мёртвой.

`dns_failed` и `url_not_allowed` разделены намеренно: несуществующий домен — обычная судьба
старой ссылки, а адрес во внутренней сети — совсем другой разговор, и пользователю о них
надо сообщать по-разному. На безопасность деление не влияет, соединения нет в обоих случаях.

## `admin_notepad`

Одна строка с `id = 1` — общий блокнот для админов. Не про пользовательские данные, просто
разделяемая заметка в админке.
