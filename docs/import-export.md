# Экспорт и импорт дерева

Обе ручки — только для админа, обе в `server/routes/nodes.js`.

## Формат файла

`GET /api/nodes/export` отдаёт один самодостаточный JSON:

```json
{
  "app": "spritenote",
  "exportedAt": "2026-08-07T13:00:00.000Z",
  "nodes": [
    { "localId": 0, "parentLocalId": null, "type": "folder", "name": "Работа",
      "description": null, "url": null, "content": null },
    { "localId": 1, "parentLocalId": 0, "type": "doc", "name": "Договор",
      "fileName": "dogovor.pdf", "fileBase64": "JVBERi0…" }
  ]
}
```

Настоящие `id` из БД в файл не попадают: связи выражены через сквозную нумерацию `localId` /
`parentLocalId`. Иначе файл нельзя было бы залить в другую базу или другому пользователю.

Файлы документов вложены в тот же JSON в base64 — экспорт остаётся одним файлом, но раздувается.
Ради этого для `/api/nodes/import` в `server/index.js` отдельно поднят лимит тела до 1 ГБ,
и этот `express.json()` обязан быть зарегистрирован **раньше** общего с лимитом 5 МБ.

## Импорт: только то, чего нет

`POST /api/nodes/import` добавляет недостающее и **никогда** не удаляет и не перезаписывает
существующее. Повторный импорт того же файла — пустая операция, а не вторая копия дерева.

Тождество узла — тройка **родитель + тип + имя**:

```js
identityKey(parentId, type, name)  // "12 folder работа"
```

Имя сравнивается без учёта регистра и окаймляющих пробелов — так же, как их сравнил бы сам
MariaDB с коллацией `utf8mb4_unicode_ci`, которая уже стоит на колонке.

Как это работает:

1. Перед разбором файла в память поднимается всё дерево пользователя, проиндексированное по
   `identityKey`.
2. Узлы обрабатываются волнами: узел создаётся только когда его родитель уже сопоставлен
   с реальным `id` (файл не обязан быть отсортирован).
3. Если ключ уже есть в индексе — узел не создаётся, а его `localId` привязывается к
   **существующему** `id`. Поэтому новые дети приезжают внутрь уже имеющейся папки, а не
   в её дубликат.
4. Созданные узлы тут же попадают в индекс, так что дубли **внутри одного файла** схлопываются
   так же, как дубли относительно базы.

Проверка на дубль стоит **до** записи файла документа — иначе повторный импорт оставлял бы
в `data/uploads/` файлы, на которые никто не ссылается.

Ответ:

```json
{ "ok": true, "imported": 3, "skipped": 5, "unresolved": 0 }
```

- `imported` — сколько узлов создано
- `skipped` — сколько уже было
- `unresolved` — узлы, чей родитель так и не нашёлся (битый или обрезанный файл); они
  молча не импортируются

## Чего эта схема сознательно не делает

- **Не обновляет существующие узлы.** Если в файле у ссылки другое описание, а имя то же —
  победит то, что уже в базе. Правило «добавлять только то, чего нет», а не «синхронизировать».
- **Не различает узлы с одинаковыми именами.** Две разные ссылки с одним названием в одной папке
  считаются одним узлом. В интерфейсе такие всё равно неразличимы, так что цена невелика.
- **Не переносит даты создания.** У импортированных узлов `created_at` — момент импорта.
